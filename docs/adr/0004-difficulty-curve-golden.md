# 0004. 難易度カーブの回帰検出（決定論リプレイ）

## Status

proposed（2026-09-17）

> このリポジトリの現時点の判断を記録したものです。一般的な best practice の主張ではありません。

## Context

[ADR 0001](0001-test-layering-and-injected-time.md) で L2（決定論リプレイによる難易度カーブの
回帰検出）を未整備として残していた。

L0 契約が難易度について見ているのは「単調非減少」「上限がある」「参照ボットが規定秒数
生存できる」の3点だけで、いずれも幅の広い条件である。日次フローが毎日1件ずつ
「小さな安全な改善」としてバランスを触ると、1回ごとには L0 を通り続けたまま、
数週間でカーブが別物になりうる。実際、ジャンプ力を `-300` から `-320` に変えても
L0 は全項目通る。

一方で「面白さが変わっていないこと」を機械的に定義するのは無理なので、
*変わったことを検出して人間に判断させる*までを目標にした。

## Decision

### 1. シードを固定した参照ボットの再生を指標にすることにした

`tests/support/replay.gd` がシードを固定してボットに操作させ、決まった時刻
（10 / 30 / 60 / 120 / 180 秒）で2つの値を記録する。

- **難易度** — `host.get_difficulty()`。速度カーブの変化が直接出る。
- **参照ボットの操作回数** — `act` 演出イベントの累積回数。

### 2. 操作回数を主要な指標に選んだ

難易度の数値はモードごとに意味が違い、実装を変えれば単位も変わる。一方
「規定時間内にボットが何回タップしたか」は**ジャンルに依存しない行動指標**で、
スポーン間隔でもジャンプ性能でも、体感の変化として現れたものはここに出る。

実測で確認した挙動：

| 変更 | L0 | L2（難易度） | L2（操作回数） |
| --- | --- | --- | --- |
| `SPEED_PER_SECOND` 5.0 → 6.0 | 通過 | 検出（250→260 等） | 通過 |
| `jump_force` -300 → -320 | 通過 | 通過 | **検出（53→51 回）** |
| `SPAWN_INTERVAL_RANDOM` 1.5 → 1.2 | 通過 | 通過 | **検出（26→28 回）** |

ジャンプ性能とスポーン密度の変更は、操作回数を見なければ検出できなかった。

### 3. 基準値を `tests/golden/<mode>.json` に置くことにした

ここが設計の要。`modes/` 配下に置くと、日次フローが「テストが落ちたので基準値を
更新する」という最短経路を取れてしまい、回帰検出が意味を失う。

`tests/` は CI の `guard` ジョブが保護しているため、自動フローからは更新できない。
バランスを意図的に変えたときは、人間が `bash scripts/record-golden.sh` で記録し直す。
日次フローのプロンプトにも「基準値は更新できない。落ちたら別の改善を選べ」と明示した。

### 4. 記録と照合で同じ再生コードを通すことにした

`tests/tools/record_golden.gd`（記録）と `tests/contract/test_difficulty_curve.gd`（照合）は
どちらも `tests/support/replay.gd` を呼ぶ。記録手順と検証手順がずれて、
再生しても再現しない基準値ができる事故を構造的に防ぐ。

### 5. 基準値が無いモードは通すことにした

新しく追加されたモードには比較対象となる過去のカーブが存在しない。この場合テストは
失敗ではなく通過させるが、**必ずその旨を出力する**。

```
※ モード 'flappy' のゴールデン値が未設定のため回帰検出は行われていません
  固定するには: bash scripts/record-golden.sh
```

黙って飛ばすテストは「通っている」と誤読される。回帰検出は人間がカーブを固定した
時点から始まる、という状態を毎回可視化する。

## Consequences

- Good: 1回ごとには L0 を通る小さなバランス調整の積み重ねを検出できるようになった。
- Good: 基準値を自動フローが更新できないため、「テストが落ちたから基準値を直す」という
  最短経路が塞がれている。バランス変更は必ず人間の判断を経る。
- Good: 操作回数という指標がジャンルに依存しないので、新しいモードでもそのまま使える。
- Bad: **意図的なバランス調整のたびに人手が1ステップ増える。** 日次フローは
  バランスを触れなくなったに近い（触ると落ちて、別の改善に切り替えることになる）。
  改善の幅を狭めた副作用がある。
- Bad: 基準値はボットの実装に依存する。ボットを改良すると操作回数が変わるので、
  ボットを変えたら記録し直すことになる。ボットとカーブの変化が区別できない。
- Bad: 許容幅（難易度 ±1.0、操作回数 ±1）は実測から決めた値で、根拠は
  「浮動小数の累積で1フレームぶんずれても落ちない程度」でしかない。
  180秒で81回の操作に対する ±1 が適切かは、運用してみないと分からない。
- Bad: 再生に 180 秒ぶん × 1シードを使うため、契約テスト全体の実行時間が増える
  （とはいえ実測で1秒未満のまま）。

## Confirmation

**CI が落とすもの（＝実際に強制されること）**

- 有効なモードに基準値がある場合、難易度と操作回数が許容幅に収まっていること。
  `tests/contract/test_difficulty_curve.gd`。`ci.yml` の `contract` ジョブが実行する。
- `opencode/` 始まりのブランチからの PR が `tests/**`（`tests/golden/` を含む）を
  変更していないこと。`ci.yml` の `guard` ジョブ。

**指針にとどめるもの（＝破っても何も起きないこと）**

- 基準値が無いモードを放置しないという運用（テストは通るので、出力を読む人がいないと
  いつまでも回帰検出が始まらない）。
- チェックポイントの時刻とシードの選び方。
- 許容幅の値。
