# 0009. スコア加点のフック: モードがホストの `add_score()` で加点する

## Status

proposed（2026-10-02）

> このリポジトリの現時点の判断を記録したものです。一般的な best practice の主張ではありません。

## Context

スコアは `core/game_host.gd` が経過秒数として加算している（`score += delta`）。モードはスコアに
触れないため、「うまくやったら加点する」設計ができない。ADR 0008 でも「投擲回数が少ないほど高得点」を
見送った理由がこれで、「モードから加点できるフックは `core/` の変更を伴うので、別の変更で扱う」と記していた。

## Decision

1. ホストに `add_score(points: float)` を足す。モードは `host.add_score(...)` で点数を渡す。
2. 加点は `PLAYING` 中の正の値だけを受け付ける。`START` / `GAME_OVER` 中や 0 以下の値は無視する。
   GAME_OVER 後に遅れて呼ばれても記録が動かないようにするため。
3. スコアの所有者はホストのまま。モードに `score` の書き込みを許さず、読み書きの経路は加点の一本に絞る。
4. 経過時間による加算（`score += delta`）は変えない。既存モードの挙動、`tests/golden/` の難易度カーブには影響しない。
5. このフックを使う個別モードの加点ルールは、この ADR の対象外（モードごとに別の変更で決める）。

## Consequences

- モードがリスクと報酬を結べるようになる。企画書 001 の「低空飛行中は倍率が上がる」のような設計が可能になる。
- 加点が経過時間に上乗せされるため、加点を使うモードではスコアの尺度が「秒」から外れる。
  ハイスコアは従来の記録と直接比較できなくなる点に注意（フックだけを足した今回は変化なし）。
- `core/` の変更なので、自動フロー（`opencode/` ブランチ）からはこの種の変更ができない。人間が行う。

## Confirmation

- `tests/contract/test_score_bonus.gd` が、PLAYING 中の加点、START / GAME_OVER 中と 0 以下の無視、
  表示の更新、再開時のリセットを検査する（CI が落とす）。
- 実際にモードが加点したときの体感は、実プレイでの確認が必要で CI では見ていない。
