# 0002. core と modes への分離、およびモードレジストリ

## Status

proposed（2026-09-17）。[ADR 0001](0001-test-layering-and-injected-time.md) の決定6
「`core/` と `modes/` への分離は今回は行わない」を置き換える。

> このリポジトリの現時点の判断を記録したものです。一般的な best practice の主張ではありません。

## Context

ADR 0001 で L0 契約テストを整えたが、週次の大型アップデート（ジャンル変更を含む）を
自動化フローに任せるための構造がまだ無かった。当時の `main.gd` は、ジャンルが変わっても
不変な部分（状態機械・スコア・ハイスコア・入力経路）と、ランナー固有の部分
（障害物のスポーン、速度カーブ、当たり判定）が同じ264行に混ざっていた。

この状態で opencode に「ジャンルを変えろ」と指示すると、次の2つが避けられない。

- 不変であるべき部分まで書き換わる。1ボタンという制約自体が壊れうる。
- 変更範囲をパス単位で機械的に縛れない。プロンプトで禁止しても破られる。

またロールバックの単位が無い。大型更新が失敗したとき、戻す対象を特定できない。

## Decision

### 1. ジャンルに依存しない部分を `core/` に切り出すことにした

`core/game_host.gd` が持つのは、START / PLAYING / GAME_OVER の状態機械、1アクションだけで
一周する再開フロー、スコアとハイスコアの永続化、唯一の入力経路、演出イベントの発火、
モードの読み込み。ゲームプレイは一切持たない。

### 2. ゲームプレイを `modes/<id>/` に閉じ込めることにした

`modes/runner/` に、モードスクリプト・シーン・アセット参照・`spec.json`・参照ボットを置く。
ビジュアルと SE もモードのシーン内にあるので、演出の刷新は `modes/` 配下だけで完結する。

### 3. モードのインターフェースを3点に絞ることにした

`core/game_mode.gd`:

- **入力は `mode_tick(delta, act_pressed, act_released)` の引数だけ。** モードは `_input` を
  持たない。ジャンルの差は「タップが何を意味するか」で吸収する。これにより 1ボタンという
  制約がアーキテクチャ側で強制され、生成エージェントがそれを破る手段が無くなる。
- **時間も同じ引数から来る。** モードは `_process` を持たない。テストが固定タイムステップで
  再生できる唯一の条件がこれ。
- **スコア・ハイスコア・UI・再開フローはホストが所有する。** 週次更新の射程外に置く。

この2つ（`_input` と `_process` を持たないこと）は
`tests/contract/test_input_isolation.gd` が spec の `input_isolated_scripts` を使って
静的に検査する。

### 4. `modes/registry.json` の `active` でモードを切り替えることにした

週次更新は「新しいモードを追加して `active` を切り替える」PR になる。旧モードは消さない。
**事故ったときに1行の revert で先週に戻せること**が、大型更新を毎週回すうえでの前提だと
判断した。契約テストも `active` が指す spec を読むので、テストコードは変わらない。

### 5. 自動改善フローの射程を CI で縛ることにした

`ci.yml` の `guard` ジョブが、`opencode/` 始まりのブランチからの PR に
`core/**`・`tests/contract/**`・`tests/support/**`・`tests/run_tests.gd`・
`.github/workflows/**` の変更が含まれていたら落とす。プロンプトでも同じ境界を伝えるが、
プロンプトは破られるので CI 側が本命。

## Consequences

- Good: 週次更新が触ってよい範囲が `modes/` と `assets/` にパス単位で限定され、機械的に
  検証できるようになった。
- Good: ロールバックの単位がジャンル単位に揃った。`active` を戻すだけで巻き戻せる。
- Good: 演出の実体（パーティクル・SE のノード）がモードのシーンに入ったので、ホストは
  見た目や音を一切知らない。ビジュアル刷新がホストに波及しない。
- Bad: **ADR 0001 の「移設の正しさは L0 が緑のままであることで担保できる」は言いすぎだった。**
  実際にはテスト側で3箇所の参照を書き換える必要があった（`main.FEEDBACK_MAP` →
  `main.get_feedback_map()`、`main.game_speed` → `main.get_difficulty()`、
  プレイヤー取得をモード経由に）。L0 が不変なのは*ジャンル*が変わるときで、
  *アーキテクチャ*が変わるときは変更が要る。層の切り方（安定性の地平線）は
  ジャンル変更に対する不変性を意味しており、構造変更に対する不変性ではない。
- Bad: ノード階層が一段深くなった（`Main/ModeContainer/RunnerMode/Player`）。Godot の
  エディタで触るときの取り回しが少し悪くなる。
- Bad: モードが増えるほど `modes/` の総量が増える。旧モードを消さない方針なので、
  エクスポートサイズは単調増加する。どこかで「N世代前は消す」判断が必要になる。
- Bad: L2（決定論リプレイによる難易度カーブの回帰検出）は引き続き未整備。

## Confirmation

**CI が落とすもの（＝実際に強制されること）**

- モードが `_process` / `_input` / `Input` を持たないこと。`tests/contract/test_input_isolation.gd`
  が spec の `input_isolated_scripts` に挙がったスクリプトを静的に検査する。
- `opencode/` 始まりのブランチからの PR が `core/**` を変更していないこと。
  `ci.yml` の `guard` ジョブ。
- L0 契約テスト全項目と Web エクスポート。`ci.yml` の `contract` ジョブ。

**指針にとどめるもの（＝破っても何も起きないこと）**

- 旧モードを消さないという運用。
- 新モードに参照ボットを同梱するという運用（`spec.json` に `bot` が無ければ
  プレイアビリティテストは落ちるが、モードを追加せず `active` も変えなければ何も起きない）。
- `modes/<id>/` 配下のファイル構成。
