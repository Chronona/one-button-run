# 0006. 未実装の企画書を週次アップデートの入力にする

## Status

proposed（2026-09-20）

> このリポジトリの現時点の判断を記録したものです。一般的な best practice の主張ではありません。

## Context

ゲームモードの企画書が2本できた。

- 企画書A: [振り子グラップル・ランナー](../proposals/001-grapple-pendulum-runner.md)
- 企画書B: [チャージ投擲ローグライク](../proposals/002-charge-throw-roguelike.md)

[ADR 0003](0003-weekly-large-update-automation.md) で決めた週次の大型アップデートは、
エージェントが自分でジャンルを選ぶ設計になっている（`weekly-update.yml` のプロンプト:
"Add a NEW mode under `modes/<id>/` where `<id>` is a short lowercase identifier for the
genre (e.g. `flappy`, `rhythm`, `dodger`)"）。このままでは企画書は永久に実装されない。

エージェントに企画書を読ませる素直な方法は `weekly-update.yml` のプロンプトを書き換える
ことだが、2つ引っかかる。

- `.github/workflows/**` は `ci.yml` の `guard` ジョブの保護対象で、自動フロー自身は
  変更できない。人間は変更できるので不可能ではない。
- プロンプトを変えるとフローの挙動全体が変わり、ロールバックの単位がワークフローになる。
  「企画書を入力にする」という運用だけを足したいのに、射程が広すぎる。

またA案とB案のどちらを先に実装するかも決まっていなかった。企画書B自身は
「Bを先に完成させ、続行判断が出るまでAには着手しない」を推奨している。

## Decision

### 1. 企画書を `docs/proposals/` に置き、リポジトリの一部にすることにした

企画書がローカルの手元にあるだけでは、実装する主体（週次エージェント）から見えない。
リポジトリに入れることで、エージェントの到達範囲に入る。

GitHub Issue ではなくリポジトリ内のファイルにしたのは、**週次エージェントが読むのは
チェックアウトしたリポジトリの中身だけで、Issue は読まない**ため。

### 2. 未実装の判定を `modes/<mode_id>/` の有無にすることにした

各企画書は先頭に `mode_id` と `priority` を持ち、`modes/<mode_id>/` が存在しなければ
未実装とみなす。

企画書側に「実装済み」フラグを持たせる案もあったが、**ディレクトリは実装すれば必ず
できる**ので、状態の更新を忘れても破綻しない方を選んだ。`docs/` は `guard` の保護対象
ではないためエージェントがフラグを更新すること自体は可能だが、それに依存しない。

### 3. エージェントへの指示は ADR 0002 の末尾に置くことにした

`weekly-update.yml` のプロンプトは1つのファイルだけを名指しで読ませている。

> Read `docs/adr/0002-core-modes-split.md` first. It describes the architecture you must work within.

**ワークフローを変更せずにエージェントの行動を変えられる場所は、事実上ここだけ**なので、
[ADR 0002](0002-core-modes-split.md) の末尾に「週次エージェントへの実行指示」節を足した。

ポインタ（「詳細は 0006 を読め」）ではなく自己完結した手順にしたのは、2ファイル目を
読ませると追従率が落ちるため。週次のモデルは無料枠（`opencode/muse-spark-1.3-contributor-free`）で、
指示追従の信頼性に限度がある。

[ADR 0002](0002-core-modes-split.md) の決定1〜5は変更していない。
`docs/adr/README.md` は「決定を変えたくなったら、既存の ADR を書き換えるのではなく、
新しい ADR を足して古い方の Status を更新します」と定めており、**決定の記録はこのファイル
（0006）にある**。0002 に置いたのは、その決定を実行に移すための手順である。

### 4. 実装順序は A（`grapple`）→ B（`charge`）にすることにした

**企画書B自身の推奨とは逆にした。** 企画書Bの推奨は「B案のほうが実装コストが低い」
という前提に立っているが、この前提はこのリポジトリでは成立しない。

**(a) 既存資産からの差分で測ると逆転する。**
`modes/flappy/flappy_mode.gd` が既に持っているのは、質点の位置と速度、重力積分、
スクロール速度カーブと上限、障害物のスポーンと消去、矩形衝突、演出イベントの発火。
A案はこれに「ロープの拘束と解除」を足したもので、自動前進はスクロール、アンカーは
`gate.gd` の置き換え、地面接触死は床判定がそのまま使える。B案は固定発射台で
スクロールが無く、角度メーター・パワーバー・複数標的・ステージ遷移・残弾管理を
すべて新規に書くことになる。

**(b) L0 契約との衝突がA案はほぼ無い。**

| 契約 | A案 | B案 |
| --- | --- | --- |
| 無操作なら有限時間で必ず失敗（`_test_idle_death`） | ✓ 地面接触で即死。ホールドしなければ落ちる | ✗「即死ではない」と衝突。見送りタイマーの追加が要る |
| 難易度は単調非減少かつ上限あり（`_test_difficulty_shape`） | ✓ 難易度＝スクロール速度、アップグレード＝プレイヤー能力で直交 | △ アップグレードが難易度そのものを下げる |
| スコアは経過秒数（`core/game_host.gd`） | ✓ 到達距離と比例する | ✗ ステージ数をスコアにしたいが core は変更不可 |

**(c) `core/game_mode.gd` のインターフェースの形に一致する。**
`mode_tick(delta, act_pressed, act_released)` の3引数に対し、企画書Aは
「3状態それぞれに独立した意味を持たせる。同じ量を重複して制御させない」（押下＝フック射出、
継続＝ロープ長、解放＝射出角度）。B案はタップとホールドが同じ2つの量を同時に動かす。

**(d) 参照ボットが企画の成否判定を兼ねる。**
企画書Aの最重要指標は「全員が最下点でしか離さないなら、判断が存在していないことになり、
この案の前提が崩れる」。これは「常に最下点で離すボット」が
`bot_min_survival_seconds` を生存できるかで機械的に測れる。
[ADR 0003](0003-weekly-large-update-automation.md) 決定2でボットの同梱を必須にしたことが、
そのまま企画の検証に使える。

なお、A案唯一の新しい難所は可変 delta での数値積分である。振り子は
`θ̈ = -(g/L)sinθ` で非線形なため、実プレイ（可変 delta）とテスト（1/60 固定）で
挙動が食い違いうる。対策は企画書Aの「このリポジトリで実装する際の制約」に書いた。

### 5. 企画書本体は書き換えないことにした

企画書は元の判断の記録なので残す。このリポジトリ固有の事情は、各ファイル末尾の
「このリポジトリで実装する際の制約」節にすべて追記する。企画書本体と契約が衝突した
場合に**契約を曲げてはならない**ことも、その節に明記した。

### 6. 強制はせず、指針にとどめることにした

CI は「1ボタンで遊べるか」は判定できるが、「企画書のとおりに作ったか」は判定できない。
エージェントが企画書を無視して自分でジャンルを選んでも、契約テストが緑なら PR は通る。

これを機械的に強制する仕組みは作らない。守られなかったときに気づけるのは、人間が PR を
レビューする時点だけである（[ADR 0003](0003-weekly-large-update-automation.md) 決定5
「自動マージしない」）。失敗しても損害は小さく、企画書を無視した PR をマージしなければ
よいだけなので、強制の仕組みに見合わないと判断した。

## Consequences

- Good: 週次アップデートが「エージェントが思いついたジャンル」から「人間が決めた企画」に
  変わる。ジャンルの選択という一番大きな判断が人間の側に戻る。
- Good: ワークフローを変更していないので、この運用をやめたいときは ADR 0002 の追記節を
  消すだけで元に戻る。ロールバックの単位が小さい。
- Good: 企画書の「このリポジトリで実装する際の制約」節が、L0 契約との衝突をあらかじめ
  潰しておく場所になった。エージェントが契約テストで何度も落ちて時間を溶かす分を減らせる
  （週次は 60 分の制限がある）。
- Bad: **指針でしかない。** エージェントが企画書を無視しても CI は何も言わない。
  週次のモデルが無料枠であることを考えると、追従率は高くないかもしれない。
- Bad: ADR 0002 が「core と modes の分離」という本来の主題に加えて、週次エージェントへの
  実行指示という別の役割を持つことになった。0002 を読む人間にとってはノイズになる。
  これは `weekly-update.yml` のプロンプトが 0002 だけを名指ししていることの帰結であり、
  プロンプトを変更できる人間が「読むべきファイル」を増やせば解消する。
- Bad: 企画書が尽きたときの挙動を「エージェントが自分でジャンルを選ぶ」に戻す一文に
  依存している。この一文が読み飛ばされると、週次が静かに何もしなくなる。
- Bad: 実装順序を A → B に決めたが、これは既存資産と契約適合から導いた判断であって、
  **どちらが面白いかの判断ではない**。A案が段階的な検証（最下点固定ボットが生存できるか）
  で崩れた場合、B案へ移行する。企画書A自身も「その場合はB案へ移行する」と書いている。

## Confirmation

**CI が落とすもの（＝実際に強制されること）**

- なし。この ADR の決定はどれも CI で検査していない。

作られたモードが遊べるかどうかは、これまでどおり L0 契約テストが判定する
（[ADR 0003](0003-weekly-large-update-automation.md) 決定2）。この ADR が足したのは
「何を作るか」の指示であり、「作られたものが妥当か」の検査ではない。

**指針にとどめるもの（＝破っても何も起きないこと）**

- 週次エージェントが未実装の企画書を優先すること。
- `priority` の順に実装すること。
- 企画書本体を書き換えず、制約を末尾の節に追記すること。
- 企画書が尽きたときに限りエージェントが自分でジャンルを選ぶこと。
