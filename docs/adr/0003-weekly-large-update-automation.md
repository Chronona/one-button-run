# 0003. 週次大型アップデートの自動化

## Status

proposed（2026-09-17）

> このリポジトリの現時点の判断を記録したものです。一般的な best practice の主張ではありません。

## Context

やりたいことは「1ボタン(タップ)操作で遊べる」を維持したまま、毎週大型アップデート
（機能向上・ビジュアルと SE の刷新・ゲームジャンルそのものの変更）を opencode で回すこと。

[ADR 0002](0002-core-modes-split.md) で `core/` と `modes/` を分離し、`registry.json` の
`active` でモードを切り替える構造になったので、「新しいモードを追加して `active` を
切り替える」形の変更として表現できるようになった。あとはそれを回す仕組みと、
受け入れ条件をどこに置くかを決める必要がある。

既存の日次フロー（`auto-improve.yml`）は「小さな安全な改善を1件」という射程で、
ジャンル変更のような大きな変更は明示的に禁止している。週次は別の射程を持つ別の
ワークフローにするのが素直だと判断した。

## Decision

### 1. 週次を別ワークフロー（`weekly-update.yml`）にすることにした

日次と週次で求めるものが正反対（小さく安全に / 大きく変える）なので、同じワークフローの
プロンプト分岐で扱うより、別ファイルにしてそれぞれのプロンプトを独立させる。
cron は日次の 06:00 JST に対して週次を月曜 07:00 JST とし、1時間ずらして衝突を避ける。

### 2. 受け入れ条件を L0 契約テストに委ねることにした

週次更新に対する品質判断を、人間のレビュー観点ではなく機械的な契約に落とす。
新モードは次を満たさなければマージできない。

- 1アクションだけで開始・失敗・再開が一周する
- 無操作なら必ず有限時間で失敗する
- 同梱の参照ボットが規定秒数生存できる
- 操作・失敗・記録更新に視覚と聴覚の反応がある
- Web エクスポートが通る

とくに**参照ボットの同梱を必須にしたこと**が効くと考えている。ボットが書けないジャンルは
人間にとっても理不尽である可能性が高いので、「ボットを同梱せよ」という要求が
そのまま品質フィルタになる。プロンプトでも「ボットが生存できないならモードを簡単にせよ、
閾値を下げるな」と明示した。

`tests/contract/test_mode_registry.gd` が、登録されている全モードについて
scene / spec / bot の存在と spec の必須項目を検査する。active なモードだけでなく
全モードを見るので、ロールバック先として残しているモードが参照切れで実は戻せない、
という状態を検出できる。

### 3. 旧モードを消さないことにした

週次更新は追加のみ。ロールバックは `registry.json` の `active` を前の ID に戻す1行で済む。
大型更新を毎週回すなら、失敗したときに1行で戻せることが前提だと判断した。

### 4. バイナリアセットの追加は求めないことにした

生成エージェントは PNG や WAV を作れない。求めても劣化したものが増えるだけなので、
見た目と音の変化は「書けるもの」で出させる：色と `modulate`、`Polygon2D` / `ColorRect`、
パーティクルのパラメータ、既存 SE の `volume_db` と `pitch_scale`。

### 5. 自動マージしないことにした

週次 PR は人間がレビューしてマージする。契約テストは「壊れていないこと」を保証するが、
「面白いこと」は保証しない。ジャンルの選択とその出来の判断は人間に残す。

## Consequences

- Good: 週次更新が「新モード追加 + `active` 切替」という定型の差分になり、レビューの
  読み方が毎週同じになる。
- Good: 1ボタン制約を守らせるためにプロンプトに頼らなくてよい。モードが入力を受け取る
  経路が `mode_tick` の引数しかないので、破る手段が構造上存在しない。
- Good: ロールバックが1行。
- Bad: **ボットの質がそのまま受け入れ判定の質になる。** リズムゲームのように「ボットは
  簡単に完璧に遊べるが人間には難しい」ジャンルでは、テストが通っても理不尽な可能性がある。
  逆にボットを書きにくいジャンルは、実際には遊べても週次が失敗し続ける。
- Bad: `modes/` が単調増加する。旧モードを消さない方針なので、エクスポートサイズも
  増え続ける。どこかで「N世代前は消す」判断が必要になる。
- Bad: アセットを増やせないため、ビジュアル変化に上限がある。「毎週ビジュアルが変わる」の
  実体は配色・形状・演出パラメータの変化にとどまる。
- Bad: 無料モデル枠で 60 分の制限を置いているので、大型更新が完走しない週がありうる。
  その場合は PR が作られないか、中途半端な PR が作られて契約テストで落ちる。後者は
  害がない（落ちる）が、前者は静かに何も起きないので気づきにくい。
- Bad: 日次と週次が同じ週に同じファイル（`modes/<active>/`）を触ると、どちらかが
  コンフリクトする。cron をずらしただけでは PR の同時存在は防げない。

## Confirmation

**CI が落とすもの（＝実際に強制されること）**

- L0 契約テスト全項目と Web エクスポート。`ci.yml` の `contract` ジョブ。
- 登録されている全モードの scene / spec / bot の存在と spec の必須項目。
  `tests/contract/test_mode_registry.gd`。
- モードが `_process` / `_input` / `Input` を持たないこと。
  `tests/contract/test_input_isolation.gd`。
- `opencode/` 始まりのブランチからの PR が `core/**`・`tests/**`・`.github/workflows/**`
  を変更していないこと。`ci.yml` の `guard` ジョブ。日次と週次の両方が対象。

**指針にとどめるもの（＝破っても何も起きないこと）**

- 旧モードを消さないという運用。
- バイナリアセットを追加しないという方針。
- 自動マージしないという運用（ブランチ保護は設定していない）。
- cron を1時間ずらすという配置。
