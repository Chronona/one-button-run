# 0001. 品質テストの3層化と、時間・入力のホスト注入

## Status

proposed（2026-09-15）。決定6「`core/` と `modes/` への分離は今回は行わない」は
[ADR 0002](0002-core-modes-split.md) に置き換えられた（2026-09-17）。

> このリポジトリの現時点の判断を記録したものです。一般的な best practice の主張ではありません。

## Context

このリポジトリでは、日次の自動改善フロー（`.github/workflows/auto-improve.yml`）が毎朝 opencode を走らせて
小さな改善 PR を作っている。しかし品質が維持されているかを検証する手段がなかった。

既存の `scripts/check.sh` が見ていたのは「GDScript がパースできる」「ヘッドレスで起動する」の2点だけで、
たとえば当たり判定を丸ごと削除しても緑のまま通る。つまり*遊べないゲーム*を検出できない。

さらにやりたいこととして、週1回の大型アップデート（機能向上・ビジュアルと SE の刷新・**ゲームジャンルそのものの変更**）を
opencode で回したい、という要求がある。ここで素朴にテストを書くと、週次アップデートのたびにテストが全部壊れる。
「テストを守るために大型更新を諦める」か「大型更新のためにテストを捨てる」かの二択になってしまうのを避けたい。

当時のコードには、テスト以前の構造的な制約もあった。

- ゲーム進行が丸ごと `_process(delta)` の中にあり、実時間を待たないと1秒ぶんも検証できない。
- `player.gd` が `Input.is_action_just_pressed()` を直接呼んでおり、入力を注入できない。
- 障害物の間隔決定に `randf()`（グローバル RNG）を使っており、同じ状況を再現できない。

## Decision

### 1. テストを「種類」ではなく「安定性の地平線」で3層に切ることにした

| 層 | 内容 | 変更頻度 | 置き場所 |
|---|---|---|---|
| L0 不変契約 | 「1ボタン(タップ)で遊べるゲームである」こと | 変えない | `tests/contract/` |
| L1 ジャンル契約 | 今週のジャンルが遊べる条件（閾値・参照ボット） | 毎週 | `tests/spec/`, `tests/bots/` |
| L2 実装詳細 | 関数単位の挙動 | 毎日 | 未整備 |

L0 に入れるのは、ジャンルがランナーからシューティングやリズムに変わっても成立する条件だけに絞った。
入力が1アクションであること、その1アクションだけで開始・失敗・再開が一周すること、無操作なら必ず死ぬこと、
参照ボットが規定秒数生存できること、操作と失敗と記録更新に反応があること、ハイスコアが永続化されること、Web に出せること。

### 2. L1 の閾値をコードではなくデータ（`tests/spec/active.spec.json`）に置くことにした

テストコードは固定で、猶予秒数・無操作死の上限・ボットの生存目標・必要な演出イベントなどの値は spec から読む。
週次でジャンルを差し替えるときに差し替わるのは spec とボットであって、テストコードは1行も変わらない。
これが「大型更新でテストが壊れない」の実体。

### 3. 時間と入力をホスト（`main.gd`）から注入することにした

- `main.tick(delta)` を公開し、`_process` はそれを呼ぶだけにした。
- 入力は `main.press_act()` / `main.release_act()` の1経路に集約し、`player.gd` から `Input` の直接参照を消した。
- 乱数をモード専用の `RandomNumberGenerator` にして `set_rng_seed()` でシードを固定できるようにした。

結果、テストは固定タイムステップでゲームを直接回せる。8シード × 180秒ぶんのプレイ検証が実時間 1 秒未満で終わる。
`tests/support/harness.gd` は `main.tscn` を実プレイと同じ構成で立ち上げたうえで `set_process(false)` するだけなので、
シーンのノード構成を変えてもテスト側の追従は要らない。

### 4. プレイアビリティの代理指標に「参照ボット」を使うことにした

「理不尽でないこと」を静的に定義するのは難しいので、`tests/bots/` のボットが規定秒数を生存できるか、で代替する。
この方式を選んだ理由は、副作用として**新ジャンルの受け入れ条件が「そのジャンルを遊べるボットを同梱すること」になる**から。
ボットが書けないジャンルは人間にとっても理不尽である可能性が高く、品質フィルタとして働くことを期待している。

### 5. 障害物の最低間隔を、定数ではなくプレイヤーの滞空時間から導出することにした

この方針を決めた直後、導入したボット生存テストが実際の欠陥を検出した。
`MIN_SPAWN_INTERVAL = 1.0` 秒に対し滞空時間は `2 × 300 / 500 = 1.2` 秒あり、速度が 350 を超えると
「着地前に次の障害物が到達する」回避不能な配置が発生していた（10シード中5シードが 43〜84 秒で詰む）。
`main.gd` のコメントは「最低間隔を保証するので詰み配置が出ない」と主張していたが、実装が満たしていなかった。

そこで最低間隔を `player.get_airtime() + SPAWN_REACTION_MARGIN` から導出する形にした。
ジャンプ性能を調整すれば間隔も自動で追従するので、同じ種類の破綻が再発しない。

### 6. `core/` と `modes/` への分離は今回は行わない

週次更新の射程を `modes/` に閉じ込める構成は有効だと考えているが、先に L0 契約テストを整えることを優先した。
移設の正しさは「L0 が緑のままであること」で担保できるので、順序としてテストが先にある方が安全だと判断した。

## Consequences

- Good: 当たり判定の削除、タップ割り当ての消失、入力経路の増殖、理不尽な難易度— いずれも自動で検出できるようになった。
  導入時に 4 種類の変異（意図的な破壊）を仕込んで、それぞれ狙った通りのテストだけが落ちることを確認している。
- Good: 週次でジャンルを差し替えても、差し替え対象は spec とボットであってテストコードではない。
- Good: 検証が実時間から切り離されたので、数百秒ぶんのプレイを CI で毎回回せる。
- Bad: ゲームプレイ側のスクリプトが `_process` と `Input` を持てなくなった。Godot の素直な書き方からは外れるので、
  この構成を知らない人（や生成エージェント）が普通に書くと契約テストが落ちる。制約の理由をこの ADR とテストのメッセージに書いて補っている。
- Bad: 「遊べる」の定義を参照ボットに委ねているため、ボットが弱いとテストも弱くなる。ボットの質がテストの質の上限になる。
- Bad: L2（決定論リプレイによる難易度カーブの回帰検出）はまだ無い。日次の細かいバランス調整の積み重ねは、今は検出できない。
- Bad: 週次の大型更新を安全に回すための `core/` と `modes/` の分離が未了なので、現時点では
  「週次更新が触ってよい範囲」をパス単位で機械的に縛れない。

## Confirmation

**CI が落とすもの（＝実際に強制されること）**

- `tests/contract/**` の全項目。`.github/workflows/ci.yml` の `contract` ジョブが PR ごとに実行する。
- Web エクスポートが通ること。同ジョブが `--export-release "Web"` を実走する。
- `opencode/` 始まりのブランチからの PR が `tests/contract/**`・`tests/support/**`・`tests/run_tests.gd`・
  `.github/workflows/**` を変更していないこと。同ファイルの `guard` ジョブが落とす。

**指針にとどめるもの（＝破っても何も起きないこと）**

- 上記の3層の切り方そのもの。
- `core/` と `modes/` への分離方針と、週次更新の射程。
- 新ジャンルにボットを同梱するという運用。

ローカルでの確認は `bash scripts/check.sh`（静的チェック＋契約テスト）または `bash scripts/test.sh`（契約テストのみ）。
